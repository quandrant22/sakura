# Сакура v3 — перестройка системы. Единое задание

Один документ на всю работу. Внешних зависимостей нет: всё, что нужно для
исполнения, включая реестр способностей, находится здесь.

База: `master = de1e799`. Работа идёт в ветке `v3`, созданной от него.
`master` остаётся рабочим до этапа 6 — Мастер пользуется системой ежедневно.

**Этап 0 выполнен и принят** (коммиты `431bc57`, `de1e799`). Он оставлен в
документе для полноты; работа начинается с этапа 1.

## Что перестраиваем и почему

Система выросла до 43 тысяч строк: `modules/` — 22 718, `agent/core/` — 6 652,
`main.py` — 3 949. Умеет 67 различных действий. Мёртвых действий нет: всё, что
объявлено, доходит до исполнителя. Система сломана не дырами, а расхождениями
между слоями — они перечислены ниже как находки 1-5, и каждая устраняется
конкретным решением новой архитектуры.

Корень беспорядка в том, что нигде не записано, что Сакура умеет. Знание
размазано по пяти местам, и добавить новый модуль можно только одним доступным
способом — ещё одной веткой в конец разбора. Это не вопрос дисциплины: места,
куда класть, не существует.

Ключевые решения, принятые Мастером и учтённые в плане:

- поведение пересматриваем, а не консервируем — где оно сегодня неверно, чиним;
- настроение и эмоциональная модель откладываются до отдельной локальной модели
  под файнтюном, в v3 их нет;
- Rust-ядро удаляется, не возрождается;
- вейк-ворд остаётся на Vosk, пока замеры не покажут обратного.

## Находка 1 — два имени у одной способности

Четыре действия существуют одновременно в двух написаниях:

| через хардкод | через LLM-роутер |
|---|---|
| `music:next` | `music_next` |
| `music:prev` | `music_prev` |
| `music:like` | `music_like` |
| `music:dislike` | `music_dislike` |
| `music:now_playing` | `music_info` |
| `music:wave` | `music_play_wave` |

Какое имя получится — зависит от того, какой слой роутинга успел ответить первым.
Примиряет это рукописная таблица перевода в `agent/core/agent.py:306`:

```python
elif action in ("music:next", "music:prev", "music:play_pause"):
    _music_action = action.replace("music:", "music_")
```

Работает, но означает, что добавить новое музыкальное действие нельзя, не тронув
три файла и не вспомнив про эту таблицу.

## Находка 2 — восемь действий LLM-роутер не знает

Есть триггеры, но в `INTENTS_PROMPT` их нет:

```
close_window:браузер   music:dislike   music:like      music:next
music:now_playing      music:prev      music:wave      screenshot:describe
```

Практический смысл: пока фраза попадает в хардкод — работает мгновенно. Стоит
сказать иначе («переключи-ка на следующую»), хардкод промахивается, LLM-роутер
про `music:next` не знает и возвращает `{"action": null}` → фраза уходит в разговор.
Сакура ответит репликой вместо того, чтобы переключить трек.

Это же объясняет, почему одни формулировки работают, а другие «она меня не поняла»
— при том что действие в системе есть.

## Находка 3 — 21 действие без быстрого пути

Обратная ситуация: 21 из 65 действий каталога доступны **только** через LLM.
Никаких триггеров, значит каждый вызов — раунд-трип к `MAIN_MODEL`, даже для
однозначных фраз.

## Находка 4 — мёртвые ветки внутри живой функции

`agent/core/agent.py:359` — третий по счёту блок диспетчеризации музыки:

```python
if action in ("music:wave", "music:play", "music:pause"):
```

Условие пропускает три действия, а тело обрабатывает девять: внутри есть ветки
для `music:like`, `music:dislike`, `music:now_playing`, `music:next`, `music:prev`.
Все пять недостижимы — их перехватывает первый блок на строке 300. Около 40 строк
кода, который выглядит рабочим и никогда не исполняется.

Всего блоков диспетчеризации музыки в агенте — три (SMTC, браузер, yamusic_app),
и граница между ними проходит не по смыслу, а по истории написания.

## Находка 5 — пять мест для одного вопроса «какие есть триггеры»

| источник | что в нём | приоритет |
|---|---|---|
| `user_commands.py` | 21 запись | 1 |
| `_HARDCODED` | 23 действия, 108 триггеров | 2 |
| `_info_hardcoded` | 20 действий | 2 |
| `INTENTS_PROMPT` | 65 действий | 3 (LLM) |
| ветки в двух хендлерах | 69 верхнеуровневых `if` | вне роутера |

Последняя строка — главная. 69 веток обходят роутер целиком: они матчат текст
сами, до того как дело дойдёт до словарей. Поэтому добавление действия в
`_HARDCODED` не гарантирует, что оно сработает — его может перехватить ветка выше.

## Что из этого следует для новой архитектуры

1. **Одно имя у действия.** Канонический идентификатор, заданный один раз. Ни
   `music:next` / `music_next`, ни таблиц перевода.
2. **Один источник триггеров.** Пять мест схлопываются в реестр. Хардкод и
   каталог для LLM генерируются из него, а не пишутся раздельно — расхождение
   находки 2 становится невозможным по построению.
3. **Диспетчеризация по данным, а не по порядку `if`.** 69 веток исчезают:
   исполнитель указан в декларации действия.
4. **Быстрый путь по умолчанию.** Раз триггеры и каталог — одно и то же, вопрос
   «есть ли у действия детерминированный путь» отпадает: он есть у всех.

## Принципы


1. **Способность объявляется один раз.** Реестр — единственный источник правды.
   Триггеры, каталог для LLM, права, подтверждения, блок возможностей в промпте,
   справка — всё генерируется из него. Ни одного места, где можно объявить
   действие в обход.
2. **Диспетчеризация по данным, не по порядку `if`.** Исполнитель указан в
   декларации. 69 веток в двух хендлерах исчезают не потому, что их переписали,
   а потому что им негде существовать.
3. **Ядро не знает про транспорт.** Telegram, голос, Android, Discord — адаптеры
   вокруг одного роутера. Дублирование между путями невозможно физически.
4. **Холодный путь изолирован от тёплого.** Настроение не имеет доступа к
   исполнению. Не по договорённости, а структурно: слой выражения получает
   результат исполнения, а не участвует в нём.
5. **Задержка — ограничение, а не пожелание.** Бюджеты записаны, замеряются,
   превышение пишется в лог. Без этого v3 через год приедет туда же.

## Бюджеты

| путь | бюджет | чем меряется |

| детерминированная команда (реестр) | 200 мс | приём текста → команда исполнителю |

## Голосовой путь

Честный стриминг: предложение готово → сразу в синтез. В v2
`stream_llm_to_tts` дренировал итератор до конца и только потом звал TTS —
переменные `buf` и `sentences` для посентенсной отдачи были объявлены и не

вызов.

# Правила выполнения


1. **Один коммит = один этап** (крупные этапы дробятся на подэтапы, но не смешиваются).
2. **После каждого коммита:** `python -m py_compile` по изменённым файлам,
   `ruff check --select F821,B023 .`, `pytest tests/ -q`.
   **В отчёт прикладывается дословный вывод каждой команды, а не вердикт.**
   Не «ruff: 0 ошибок», а строка, которую команда напечатала. Не «331 passed»,
   а последняя строка вывода pytest. Причина: вердикт нельзя проверить, не
   повторив команду, и один раз это уже пропустило живой краш в `master`.
3. **Новый код пишется в `sakura_core/`, `capabilities/`, `adapters/`.** Старый не трогается,
   пока его домен не переехал. Никаких «заодно поправил».
4. **Ничего не удаляется, пока не подтверждено, что новый путь работает.** Удаление
   старого — всегда отдельный коммит, следующий за коммитом переезда.
5. **Запрещено:** менять протокол WebSocket без отдельного решения; менять имена
   моделей в `config.py`; добавлять зависимости без обоснования в отчёте;
   переписывать `handle_message` и `handle_voice_command` (они не переписываются,
   а исчезают на этапах 5-6, когда из них всё вынуто).
6. **Расхождение задания с кодом — остановиться и сообщить.** Не импровизировать.
7. Формат отчёта по каждому этапу:
   ```
   Этап N
   Изменено: <git diff --stat>
   py_compile: <вывод>
   ruff:       <дословный вывод>
   pytest:     <последняя строка вывода>
   Отклонения от задания: <нет / список>
   Сверх задания: <нет / файл:строка — что сделано и почему>
   Что проверено вручную: <список>
   ```
8. **Всё, что сделано сверх перечисленного в задании, декларируется отдельной
   строкой отчёта** — `файл:строка, что сделано, почему`. Если по ходу блока
   нашлось место, которого в задании не было, — чинить можно, умалчивать нельзя.
   Причина та же: незадекларированная правка сверх задания уже один раз внесла
   краш в `master`.
9. **Этот документ самодостаточен.** Всё, на что ссылаются этапы, находится
   внутри него. Внешних файлов искать не нужно. Положить его в репозиторий как
   `docs/v3/task.md` первым коммитом ветки `v3`.

# Этап 0 — Срочные правки в v2 (делать первым, в `master`)

Мастер пользуется v2 ежедневно, и там есть дефект, из-за которого агент приходится
перезапускать. Чинится до начала перестройки, в `master`, потом `v3` берётся от него.

## 0.1 Vosk накапливает решётку бесконечно

`agent/core/hearing.py:705`:

```python
wake.AcceptWaveform(data)
partial = json.loads(wake.PartialResult()).get("partial", "")
```

Возвращаемое значение `AcceptWaveform` выбрасывается. Оно означает «фраза завершена».
Штатный паттерн: `True` → `Result()` (распознаватель сбрасывается внутри себя),
`False` → `PartialResult()`.

`Result()` не вызывается никогда. Распознаватель создаётся один раз (строка 684) и
пересоздаётся только при проигрывании TTS (693) и при срабатывании вейк-ворда (708).
Всё остальное время — тишина, фоновая речь, телевизор — идёт в одну бесконечную фразу.

Симптомы в логе Мастера:

```
LOG (VoskAPI:RebuildRepository()) Rebuilding repository.
WARNING (VoskAPI:CheckMemoryUsage()) size exceeds maximum 50000000 bytes;
  effective beam was 1.55822 vs. requested beam 2
```

Последствия: ~50 МБ решётки; деградация точности вейк-ворда (декодер режет луч
агрессивнее запрошенного, чтобы влезть в лимит); и главное — обработка блока
перестаёт укладываться в реальное время, звук копится во входном буфере, весь поток
слуха едет с плавающим отставанием.

**Правка:**

```python
if wake.AcceptWaveform(data):
    wake.Result()          # фраза закрыта, внутреннее состояние сброшено
    partial = ""
else:
    partial = json.loads(wake.PartialResult()).get("partial", "")
```

## 0.2 Страховка на случай непрерывного шума

Если тишины долго нет (работающий телевизор, музыка в комнате), `AcceptWaveform`
может не возвращать `True` очень долго. Добавить принудительное пересоздание:

```python
_wake_born = time.monotonic()
_WAKE_MAX_AGE = 60.0   # секунд непрерывного накопления
```

в цикле, рядом с существующими пересозданиями:

```python
if time.monotonic() - _wake_born > _WAKE_MAX_AGE:
    wake = KaldiRecognizer(model, config.MIC_RATE)
    _wake_born = time.monotonic()
```

Три существующих места пересоздания (`is_playing`, вейк-ворд, это новое) должны
обновлять `_wake_born`. Вынести в маленький локальный хелпер, чтобы не забыть.

## 0.3 Замер бюджета блока

Цикл читает блоками `MIC_BLOCK = 512` при `MIC_RATE = 16000` — это 32 мс звука.
Значит на обработку блока есть 32 мс. Сейчас никто не знает, укладывается ли он.

Добавить замер вокруг `AcceptWaveform` + `PartialResult` с предупреждением:

```python
_t0 = time.monotonic()
... обработка блока ...
_dt = (time.monotonic() - _t0) * 1000
if _dt > 32:
    log.warning(f"[hearing] блок обработан за {_dt:.0f}мс при бюджете 32мс — поток отстаёт")
```

Логировать не чаще раза в 5 секунд, иначе лог захлебнётся.

**Это ключевой замер для этапа 4.** Без него решение про замену Vosk принимать нельзя.

## Критерии приёмки этапа 0

1. `git diff --stat` — только `agent/core/hearing.py`, не более ~30 строк.
2. `python -m py_compile agent/core/hearing.py`.
3. `pytest tests/ -q` — 331 passed.
4. Ручная проверка Мастером: агент работает **сутки без перезапуска**, в логе нет
   `Rebuilding repository`, предупреждений о превышении 32 мс нет или они единичные.
5. Коммит в `master`, запушен. Ветка `v3` создаётся от него.

**Если после суток предупреждения о превышении бюджета остались — сообщить с цифрами.**
Это меняет план этапа 4.

# Этап 1 — Реестр

**Новые файлы:** `sakura_core/registry.py`, `sakura_core/capabilities.yaml` — собирается из
приложения в конце этого документа (67 деклараций). Скопировать в `sakura_core/capabilities.yaml`
как есть, включая шапку с правилами матчинга.

## 1.1 Загрузка и модель данных

`sakura_core/registry.py` читает YAML и отдаёт список деклараций. Поля:

| поле | тип | обязательное | смысл |
|---|---|---|---|
| `id` | str | да | канонический `domain.verb` |
| `legacy` | list[str] | нет | имена из v2, временное, удаляется после переноса |
| `desc` | str | да | идёт в каталог для LLM |
| `executor` | `vps` \| `agent` | да | кто исполняет |
| `reversible` | bool | да | можно ли откатить |
| `confirm` | bool | да | нужно ли подтверждение Мастера |
| `triggers` | list[str] | да, непустой | детерминированные фразы |
| `context` | str | нет | `playing:music` \| `window:youtube` \| `window:browser` |

Зависимость: `pyyaml`. Единственная новая, обоснование — реестр в коде был бы
ровно той проблемой, от которой уходим.

## 1.2 Матчинг — контракт, а не деталь

Два правила, нарушение любого ломает реестр:

**Только по границам слов.** Подстрока внутри слова совпадением не считается.
Иначе `лайк` срабатывает внутри `дизлайк`, `дизлайкни`, `мои лайки` — проверено,
11 таких пересечений.

**Выигрывает самый длинный совпавший триггер, не первый по порядку.** Проверено,
14 вложений, из них опасное:

```
'нравится'      ⊂ 'не нравится'
'нравится трек' ⊂ 'не нравится трек'
```

При матчинге «первый совпавший» фраза «не нравится трек» распознаётся как лайк.

Реализация: индекс триггеров строится при загрузке, поиск идёт от самых длинных
к коротким, регулярка с `(?<!\w)` / `(?!\w)` (не `\b` — так же, как в
`sakura_core/state.py:check_confirmation`, который это уже делает правильно).

## 1.3 Валидация — падать на старте, а не в бою

`validate()` вызывается при загрузке и **бросает исключение**, если:

- два действия имеют одинаковый `id`;
- один триггер принадлежит двум действиям, и **хотя бы у одного нет `context`**
  (с `context` это законно: `перемотай вперёд` делят `music.seek_forward` и
  `youtube.forward`, разводятся контекстом);
- `triggers` пустой;
- `executor` не из списка;
- `context` не из списка допустимых значений.

Это самое важное в этапе. Смысл реестра в том, что двадцатое действие нельзя
добавить, тихо сломав девятнадцатое. Валидация — то, что это обеспечивает.

## 1.4 Генерация каталога для LLM

`build_llm_catalog()` собирает текст каталога из `id` + `desc` всех деклараций.
Это заменяет `INTENTS_PROMPT` из `modules/command_router.py`.

Находка 2 инвентаризации (восемь действий имели триггеры, но отсутствовали в
каталоге, поэтому LLM про них не знал и возвращал `null`) становится невозможной
по построению: триггеры и каталог — одни и те же данные.

## Критерии приёмки этапа 1

1. `from core.registry import load; r = load()` → 67 деклараций, без исключений.
2. `validate()` на текущем YAML проходит.
3. Негативные тесты (написать в `tests/test_registry.py`): дубль `id`, коллизия
   триггеров без `context`, пустые `triggers`, неизвестный `executor` — каждый

4. Тесты матчинга: `не нравится трек` → `music.dislike` (не `like`);

# Этап 4 — Голосовой адаптер и решение по слуху

**Новые файлы:** `adapters/voice.py`, `sakura_core/budget.py`, `sakura_core/llm.py`.

## 4.1 Честный стриминг в TTS

В v2 `modules/tts_server.py:598` функция называется `stream_llm_to_tts`, но
дренирует итератор до конца и только потом зовёт синтез. Переменные `buf` и
`sentences` для посентенсной отдачи объявлены и не используются — `ruff` видит их
как `F841`. Докстринга обещает «~400-600 мс до первого звука», что при таком коде
невозможно.

В v3 стриминг — основа: предложение готово → сразу в синтез. Двухстадийный
`_stream_two_stage` ниже по течению сделан правильно и переносится как есть.

## 4.2 Клиенты LLM

`sakura_core/llm.py` держит клиентов в кэше. В v2 `genai.Client(api_key=key)` создавался
заново в `modules/intent_classifier.py:176` и `modules/command_router.py:573` —
TLS-хендшейк на каждый вызов. Плюс таймауты (в v2 их не было: зависший запрос
подвешивал весь голосовой путь) и фолбэк моделей.

## 4.3 Бюджеты

`sakura_core/budget.py` — замеры этапов с предупреждением при превышении:

| путь | бюджет |
|---|---|
| детерминированная команда | 200 мс |
| команда через LLM | 1.5 с |
| первый звук голосового ответа | 800 мс |
| полный голосовой ответ | 4 с |

## 4.4 Решение по Vosk — исследование, не переделка

Vosk нужен **только** для вейк-ворда. Распознавание фразы делает GigaAM, нарезку —
Silero VAD. То есть в памяти висит целая модель ради одного слова, и она же
источник проблемы из этапа 0.

**Сначала — данные.** К этому моменту в логе есть замеры из 0.3. Если после правок
этапа 0 предупреждений о превышении 32 мс нет — Vosk остаётся, вопрос закрыт,
подэтапы ниже не выполняются.

Если предупреждения есть — оценить три варианта и **представить сравнение Мастеру,
ничего не меняя**:

**А. Убрать Vosk совсем.** Silero VAD режет речь → GigaAM распознаёт → проверяем,
начинается ли текст с «сакура». Обе модели уже в стеке, Vosk и его зависимость
удаляются полностью. Цена: GigaAM работает на каждом речевом фрагменте в комнате,
а не только после вейк-ворда. В тихой комнате это редко; при работающем телевизоре
— постоянно. Смягчается минимальной и максимальной длиной фрагмента.

**Б. openWakeWord.** Apache 2.0, ONNX, модели около 200 КБ, CPU в реальном времени.
Засада: обучение своего слова идёт через синтез примеров в Piper TTS, для русского
нужен русский голос Piper; обучающий пайплайн закреплён на версиях пакетов 2022
года и расходится с современным Python — люди собирают докер, чтобы это запустить.
Под «Сакура» это отдельная работа на выходные с неизвестным результатом.

**В. Оставить Vosk с правками этапа 0.** Дёшево, уже сделано, известное поведение.

**Рекомендация по умолчанию — В, если замеры позволяют.** Не менять работающий
компонент по гипотезе. Вариант А выглядит красиво (минус модель, минус зависимость,
минус целый класс проблем), но его цена измеряется только на живой машине Мастера,
и решение за ним.

## Критерии приёмки этапа 4

1. Голосовой путь идёт через `adapters/voice.py`.
2. Первый звук — замерен, цифра в отчёте. Бюджет 800 мс.
3. `genai.Client` создаётся один раз за процесс (проверить счётчиком).

```python
def send_threadsafe(self, obj: dict):
```

# Приложение — реестр способностей

Ниже полный реестр, 67 деклараций. Это исходные данные этапа 1 — из них
собирается `sakura_core/capabilities.yaml`. Правила матчинга в шапке — часть

```yaml
# Реестр способностей Сакуры v3
# Сгенерирован из кода 15c2509, триггеры для 39 действий дописаны вручную.
#
# ПРАВИЛА МАТЧИНГА (обязательны, иначе реестр ломается):
#   1. Только по границам слов. Подстрока внутри слова не считается совпадением —
```
