# Криптографическая защита канала «клиент ↔ сервер» в системе «Сакура»

**Пояснительная записка** к работе по дисциплине «Криптографические методы защиты информации / Информационная безопасность»

Объект: протокол `securechannel/1` (сервер `securechannel/`, клиенты `agent/`, `desktop/`, Android `mobile/`).
Состояние на 10.11.2026.

---

## Аннотация

«Сакура» — персональный ассистент из сервера на VPS и нескольких клиентов: ПК-агента,
настольного приложения и Android-приложения. Между ними передаются голосовые команды,
история переписки, память ассистента и кадры экрана. Все эти данные конфиденциальны.

Канал строится на фреймворке Noise Protocol Framework:

- `Noise_IK_25519_ChaChaPoly_BLAKE2s` для рабочих сеансов;
- `Noise_XXpsk3_25519_ChaChaPoly_BLAKE2s` для первичной привязки устройства по одноразовому коду;
- снаружи канал помещён в TLS 1.3.

Записка описывает модель угроз, архитектуру и обоснование выбора примитивов, достигаемые
свойства безопасности, результаты формальной верификации в ProVerif, проведённый аудит
и пять устранённых уязвимостей. В том числе реализована защита от атаки повтора первого
сообщения рукопожатия, найденной формальным анализом (запрос ik Q7).

## 1. Постановка задачи и модель угроз

### 1.1. Активы
| Актив | Пример | Требование |
|---|---|---|
| A1 Команды | «выключи компьютер», управление браузером | целостность, подлинность источника |
| A2 Личные данные | история чата, память, профиль | конфиденциальность |
| A3 Кадры экрана | `vision_request` | конфиденциальность |
| A4 Долговременные ключи | статические ключи X25519 сервера и устройств | секретность, возможность отзыва |

### 1.2. Модель нарушителя
Сеть описывается **моделью Долева–Яо**: нарушитель перехватывает, удаляет, переставляет,
повторяет и подделывает любые сообщения, но не обращает криптопримитивы. Рассматриваются:

- **T1, пассивный наблюдатель**: провайдер, DPI или ТСПУ. Видит весь трафик.
- **T2, активный посредник (MitM)**: способен подменять узел.
- **T3, похититель долговременного ключа**: сервера или одного устройства.
  Против него нужны прямая секретность и устойчивость к KCI.
- **T4, сетевой сканер**: ищет открытые сервисы и характерные сигнатуры протоколов.

### 1.3. Цели безопасности
| Цель | Содержание |
|---|---|
| G1 Конфиденциальность | T1/T2 не узнают содержимое A1–A3 |
| G2 Целостность | любое изменение, вставка, удаление, перестановка или повтор сообщения обнаруживаются |
| G3 Аутентификация устройства | сервер исполняет команды только от ключа из реестра |
| G4 Аутентификация сервера | клиент разговаривает только с настоящим сервером |
| G5 Свежесть / защита от повтора | повтор записанных сообщений ничего не даёт |
| G6 Прямая секретность (PFS) | компрометация долговременных ключей не раскрывает прошлые сеансы |
| G7 Отзыв | украденное устройство отключается без смены ключей остальных |
| G8 Скрытность | канал не выделяется сигнатурой среди обычного HTTPS-трафика |

## 2. Архитектура защищённого канала

### 2.1. Уровни
```
 Прикладной JSON (register, voice_command, reply, …)
 ─────────────────────────────────────────────────────
 securechannel/1: кадры "SK"|ver|type|len  +  Noise (IK / XXpsk3)   ← сквозная защита клиент–приложение
 ─────────────────────────────────────────────────────
 WebSocket
 ─────────────────────────────────────────────────────
 TLS 1.3 (wss://, Let's Encrypt, TLS_AES_256_GCM_SHA384)            ← маскировка и защита метаданных
 ─────────────────────────────────────────────────────
 TCP :443 → nginx (SNI-маршрутизация) → 127.0.0.1:8765
```
TLS завершается на обратном прокси, а Noise — внутри процесса приложения. Поэтому
компрометация прокси или его сертификата не раскрывает прикладные данные: шифртекст
Noise прокси расшифровать не может. Это и есть **сквозная (end-to-end)** защита между
клиентом и приложением.

### 2.2. Noise Protocol Framework
Noise (T. Perrin, rev. 34) — каркас протоколов аутентифицированного обмена ключами на основе
Диффи–Хеллмана. Состояние рукопожатия задаётся тремя объектами:

- `CipherState`: ключ `k` и 64-битный счётчик `n`;
- `SymmetricState`: цепной ключ `ck` и хеш транскрипта `h`;
- `HandshakeState`: ключевые пары `s`, `e`, `rs`, `re`.

Каждый DH-токен (`ee`, `es`, `se`, `ss`) вызывает `MixKey(DH(…))`:

```
ck, temp_k = HKDF(ck, DH_output)        # HKDF на HMAC-BLAKE2s, RFC 5869
k ← temp_k ; n ← 0
```
Каждое переданное значение и шифртекст подмешиваются в транскрипт: `h ← BLAKE2s(h ‖ data)`.
Полезная нагрузка шифруется AEAD с ассоциированными данными `h`. Так любое расхождение в
истории рукопожатия делает расшифровку невозможной. Пролог
`"sakura-securechannel/1\0" ‖ "session" | "pair"` подмешивается в `h` в начале и
**связывает рукопожатие с версией и назначением**: сообщение привязки нельзя выдать за
сообщение сеанса.

### 2.3. Рабочий сеанс: паттерн IK
```
IK:
  <- s                         (статический ключ сервера известен клиенту после привязки)
  ...
  -> e, es, s, ss              IK_INIT : {"v":1, "device_id", "ts"}   — только идентификация
  <- e, ee, se                 IK_RESP : {"v":1, "session", "rekey_messages", "rekey_seconds", "server_time"}
  split() → (k_C→S, k_S→C)
```
- `es = DH(e_C, s_S)`: первое сообщение может прочитать только владелец ключа сервера.
- `ss = DH(s_C, s_S)`: подлинность клиента уже в первом сообщении.
- `ee`, `se`: эфемерный обмен даёт прямую секретность и аутентифицирует сервер перед клиентом.
- Рукопожатие занимает один круг (1-RTT), клиент передаёт свой статический ключ зашифрованным:
  пассивный наблюдатель не узнаёт, какое устройство подключается (сокрытие идентичности инициатора).

Свойства полезной нагрузки по таблице спецификации Noise (§7.7), формат «аутентичность, конфиденциальность»:

| Сообщение | Аутентичность | Конфиденциальность | Комментарий |
|---|---|---|---|
| IK_INIT | 1 | 2 | аутентично, но уязвимо к KCI и **повторяемо**; поэтому несёт только идентификацию |
| IK_RESP | 2 | 4 | устойчиво к KCI, слабая прямая секретность |
| транспорт | 2 | 5 | устойчиво к KCI, **сильная прямая секретность** |

### 2.4. Привязка устройства: паттерн XXpsk3
```
XXpsk3:
  -> e
  <- e, ee, s, es
  -> s, se, psk                PSK — одноразовый 256-битный код из Telegram (QR или 8 слов)
```
Ключи сторон заранее неизвестны, поэтому применяется XX со взаимной передачей статических
ключей. Модификатор `psk3` подмешивает одноразовый секрет в последнее сообщение, и сервер
добавляет в реестр только того, кто знает код. При привязке по QR клиент **до отправки XX_3**
сверяет статический ключ сервера из XX_2 с ключом, указанным в QR. Это отсекает посредника.
Неверный PSK «сжигает» попытку: после 5 попыток код недействителен.

### 2.5. Транспорт и смена ключей
- AEAD-nonce: 96 бит = 32 нулевых бита и 64-битный счётчик `n` (little-endian), отдельный в
  каждом направлении. Принимается только кадр со **строго следующим** `n`. Повтор, пропуск,
  перестановка или изменение кадра ведут к ошибке расшифровки и разрыву соединения.
- Смена ключа (rekey) каждые 10 000 сообщений или 3600 с:
  `k ← ENCRYPT(k, 2⁶⁴−1, ∅, 0³²)[0:32]`. Это ограничивает объём данных под одним ключом
  и окно компрометации.
- Кадр: магия `"SK"`, версия, тип, длина (≤ 65 535). Любое нарушение формата закрывает
  соединение кодом 4400.

### 2.6. Режимы сервера
| `SECURE_CHANNEL` | Вход по токену (устаревший) | Noise |
|---|---|---|
| off | да | нет |
| optional | да | да |
| **required** (текущий) | **нет, закрытие 4412** | да, включая привязку XXpsk3 |

## 3. Обоснование выбора криптопримитивов

| Примитив | Назначение | Почему выбран |
|---|---|---|
| **X25519** (RFC 7748) | ECDH на кривой Curve25519 | стойкость ≈128 бит; реализации с постоянным временем; устойчивость к атакам на кручение кривой (twist security); короткие 32-байтовые ключи; нет проверок точек, которые легко забыть |
| **ChaCha20-Poly1305** (RFC 8439) | AEAD: шифрование и целостность одним вызовом | без аппаратного AES (AES-NI) работает быстро и с постоянным временем, что важно для телефонов; 256-битный ключ; тег Poly1305 128 бит; ассоциированные данные привязывают шифртекст к транскрипту |
| **BLAKE2s** (RFC 7693) | хеш транскрипта `h`, основа HMAC в HKDF | 256-битный выход (≈128 бит стойкости к коллизиям); быстрее SHA-256 на 32- и 64-битных процессорах; основан на BLAKE — финалисте конкурса SHA-3 |
| **HKDF** (RFC 5869) на HMAC-BLAKE2s | выработка ключей из результатов DH | схема extract-then-expand с доказанной стойкостью (Krawczyk, 2010); из одного DH-секрета получаются независимые цепной ключ и ключ шифрования |
| **TLS 1.3** (RFC 8446) | внешний слой | скрывает сигнатуру Noise-кадров и метаданные WebSocket; в основном режиме (EC)DHE даёт PFS (кроме режима возобновления только с PSK) |

**Почему не «HMAC + AES-GCM + свой обмен ключами».** Самостоятельная комбинация отдельных
примитивов — классический источник ошибок: порядок «шифрование/MAC», повтор nonce в GCM,
отсутствие привязки ключей к транскрипту, нет прямой секретности при общем статическом
секрете. Noise даёт проверенную композицию, у которой есть формальные анализы паттернов
(Noise Explorer, Kobeissi–Nicolas–Bhargavan, 2019), а библиотека `noiseprotocol` и учебная
реализация `securechannel/noise/` сверяются по официальным тестовым векторам.

## 4. Достигаемые свойства безопасности

| Свойство | Как достигается |
|---|---|
| **Взаимная аутентификация** | IK: сервер аутентифицирует клиента по `ss` и реестру ключей; клиент сервер — по заранее известному `s_S` (`es`, `se`) |
| **Конфиденциальность** | ChaCha20-Poly1305 на ключах из HKDF(DH); внешний TLS 1.3 |
| **Целостность** | тег Poly1305 на каждом кадре; транскрипт `h` как ассоциированные данные в рукопожатии |
| **Прямая секретность (PFS)** | эфемерные `e` в каждом рукопожатии (`ee`, `se`); эфемерные ключи уничтожаются после `split()`; rekey ограничивает окно |
| **Устойчивость к KCI** | при утечке ключа сервера нарушитель может подделать только IK_INIT (подлинность уровня 1), но не завершит сеанс от имени клиента: IK_RESP и транспорт имеют подлинность уровня 2. Это подтверждает формальный анализ (ik Q9) |
| **Защита от повтора** | транспорт: строгий 64-битный счётчик nonce. Рукопожатие: кэш эфемерных ключей и окно свежести `ts` (§6.5) |
| **Сокрытие идентичности клиента** | статический ключ клиента передаётся зашифрованным (`es`) |
| **Отзыв** | `/revoke` удаляет ключ из реестра, проверка при каждом рукопожатии |
| **Неотличимость отказов** | неизвестный ключ, отзыв, неверный PSK, повтор и битые данные вызывают одинаковую реакцию: молчание до дедлайна 5 с и код 4408. Это закрывает побочный канал по времени и по ответу |
| **Защита от перебора и исчерпания ресурсов** | лимиты: 4 параллельных рукопожатия с IP, 64 всего, 30 в минуту; 5 попыток на код привязки |

## 5. Формальная верификация (ProVerif 2.05)

Модели `docs/security/proverif/ik.pv` и `xxpsk3.pv` описывают рукопожатия в символической
модели: Диффи–Хеллман через уравнение `exp(exp(g,x),y) = exp(exp(g,y),x)`, AEAD и HKDF как
конструкторы и деструкторы, нарушитель Долева–Яо, фаза 1 с утечкой долговременных ключей
(для PFS).

Полные модели не сходятся за отведённое время (бесконечный рост базы правил при
DH-элементах от нарушителя, см. `FINDINGS.md` F1). Поэтому проверены механически
построенные сходящиеся варианты `ik_core` и `xxpsk3_auth`: **16 из 16 запросов совпали
с ожидаемыми**.

| Запрос | Свойство | Результат |
|---|---|---|
| ik Q1, Q2 | секретность транспорта в обе стороны, в том числе после утечки ключей (PFS) | ✅ доказано |
| ik Q3, Q4 | инъективная аутентификация клиента и согласие о ключе | ✅ доказано |
| ik Q5 | инъективная аутентификация сервера | ✅ доказано |
| ik Q6 | подлинность сообщения 1 без компрометации | ✅ доказано |
| **ik Q7** | **инъективность для сообщения 1** | ❌ найдена **атака повтора** IK_INIT → закрыта в реализации (§6.5) |
| xx Q1, Q2 | секретность сведений о привязке (QR и слова) | ✅ доказано |
| xx Q3 | устройство принимается только при знании PSK | ✅ доказано |
| xx Q4 | подлинность сервера после привязки | ✅ доказано |
| xx Q5 | при QR ключ сервера подтверждается до XX_3 | ✅ доказано |
| xx Q6 | без QR XX_3 уходит неподтверждённому собеседнику | ❌ ожидаемый остаточный риск → мера: привязка только по QR |
| ik Q10, xx Q9, Q10 | достижимость, то есть модель не пустая | ✅ |

Открытыми остаются запросы ik Q8 и Q9 (KCI) и xx Q7 и Q8 (офлайн-перебор PSK): для них
приведён ручной анализ по свойствам паттернов из спецификации Noise. Предложен переход на
Tamarin со встроенной теорией Диффи–Хеллмана.

## 6. Аудит безопасности и устранённые уязвимости

Аудит охватывал сетевой периметр VPS, транспорт, политику доверия, хранение секретов и
логику рукопожатия. Найденные уязвимости классифицированы по CWE.

### 6.1. V1. Передача по открытому `ws://` на нестандартном порту (CWE-319)
**Было:** WebSocket на `0.0.0.0:8765` без TLS. Шифрование Noise защищало содержимое, но
HTTP Upgrade и неизменные байты `SK\x01` в заголовке каждого кадра давали DPI устойчивую
сигнатуру. Журнал показал подключения к порту с посторонних адресов.

**Стало:** клиенты подключаются по `wss://sub.kizune-ryoiki.ru/ws-<случайный путь>`,
TLS 1.3 (`TLS_AES_256_GCM_SHA384`) на стандартном порту 443. Приложение слушает только
`127.0.0.1:8765`, а порт 8765 закрыт межсетевым экраном. Снаружи открыты только 22 и 443.
Достигается цель G8.

### 6.2. V2. Доверие к loopback за обратным прокси (CWE-348, использование менее доверенного источника)
**Было (выявлено при выкате V1):** политика `secure_policy.is_local_peer()` считала
соединения с `127.0.0.1` защищёнными (локальные процессы и VPN). За nginx **любой**
удалённый клиент приходит с `127.0.0.1`, и устаревший вход по токену получал доступ к
приватным классам данных без Noise.

**Стало:** nginx на публичной точке входа ставит заголовок `X-Sakura-Edge: 1`
(`proxy_set_header` перезаписывает заголовок клиента), а `secure_policy.via_edge()`
считает такое соединение удалённым. Метка может только **понизить** доверие, поэтому
подделать её в свою пользу нельзя. Проверено тестом и вживую: через прокси `secure=false`,
напрямую `secure=true`.

### 6.3. V3. Небезопасные права на файлы секретов (CWE-732)
**Было:** `.env` (токены API, `WS_SECRET`), `token.json` и `credentials.json` (OAuth),
`sakura.session` (сессия Telegram-аккаунта) имели права `644` и были доступны любому
пользователю ОС. **Стало:** `600`. Ключи защищённого канала уже лежали с правами
`600` в каталоге с правами `700`.

### 6.4. V4. Устаревшая аутентификация статическим токеном (CWE-294, обход аутентификации повтором перехваченных данных)
**Было:** в режиме `optional` сервер принимал JSON с общим статическим `WS_SECRET`. Токен
без nonce и привязки к сеансу: перехваченное значение переигрывается сколько угодно.

**Стало:** `SECURE_CHANNEL=required`, текстовый вход закрывается кодом 4412. По коду
проверено, что все клиенты поддерживают Noise: desktop, agent (общий
`securechannel.client`) и Android (собственная реализация на Java). По журналу с 08.11
все внешние подключения — `transport=noise`. Привязка новых устройств (XXpsk3) в
`required` работает, на это добавлен отдельный тест. Следующий шаг по регламенту —
через неделю без откатов вывести `WS_SECRET` из оборота.

### 6.5. V5. Повтор первого сообщения рукопожатия IK (ProVerif ik Q7; CWE-294)
**Суть.** IK_INIT зашифровано только на `es` и `ss`, поэтому записанное сообщение 1 можно
переслать. Сервер расшифрует его и ответит. Ключей сеанса нарушитель не получит: у него
нет эфемерного секрета клиента. Но каждый повтор открывает лишний сеанс устройства и
обновляет реестр, а это рычаг для отказа в обслуживании. Формально: инъективное
согласование для сообщения 1 нарушено.

**Решение** (`securechannel/replay.py`, формат кадров не меняется). После расшифровки и
проверки реестра сервер выполняет две проверки:

1. **Окно свежести:** отказ, если `|t_now − ts| > W`, где `W = 12 ч`. `ts` находится внутри
   AEAD-шифртекста, связанного с транскриптом `h`, поэтому подменить его без нарушения
   тега Poly1305 нельзя.
2. **Кэш эфемерных ключей:** первые 32 байта IK_INIT — открытый эфемерный ключ
   инициатора `e`. Честный клиент генерирует его заново для каждого рукопожатия, поэтому
   повтор `e` означает повтор сообщения. Кэш хранит `e` в течение `TTL = 2W`, вытесняет
   записи по истечении срока и при превышении 100 000 записей. Проверка и вставка атомарны
   (под замком).

**Обоснование достаточности.** Сообщение, принятое в момент `t`, удовлетворяет
`ts ≥ t − W` и потому проходит проверку свежести не дольше чем до `ts + W ≤ t + 2W`.
Кэш хранит его `e` ровно до `t + 2W`. Значит, в любой момент повтор отсекается либо
кэшем (пока сообщение «свежее»), либо окном `ts` (после). Отказ неотличим от прочих:
молчание и 4408 через 5 с.

**Остаточный риск:** кэш хранится в памяти процесса, поэтому после перезапуска сервера
повтор, записанный менее чем за `W` до перезапуска, пройдёт один раз.

**Формальная сторона.** В ProVerif проверка и вставка в таблицу (`get` / `insert`)
неатомарны, поэтому наивная модель кэша допускает несуществующую гонку и может дать ложный
результат. Корректная формализация — Tamarin с ограничением уникальности
`All e #i #j. Accept(e)@i & Accept(e)@j ==> #i = #j` (см. `FINDINGS.md` F2).

### 6.6. Остаточные риски
| Риск | Мера |
|---|---|
| R1. За прокси все клиенты делят один IP `127.0.0.1` в лимитере рукопожатий, что даёт DoS при утечке пути | случайный путь известен только привязанным клиентам. Полное решение — PROXY protocol через весь стек `stream` |
| R2. Привязка «только по словам» допускает офлайн-перебор PSK активным посредником (xx Q6/Q8) | регламент требует привязки по QR |
| R3. KCI для сообщения 1 (свойство паттерна IK) | в IK_INIT нет исполняемых данных; всё исполняемое идёт после завершения рукопожатия |

## 8. Заключение
Канал «Сакуры» обеспечивает взаимную аутентификацию, конфиденциальность, целостность,
прямую секретность и защиту от повтора как на транспортном уровне (строгий счётчик nonce),
так и на уровне рукопожатия: атака ik Q7 закрыта кэшем эфемерных ключей с окном свежести.
Выбор примитивов (X25519, ChaCha20-Poly1305, BLAKE2s, HKDF) соответствует современным
рекомендациям и опирается на проверенную композицию Noise. Свойства подтверждены
формальной верификацией в ProVerif (16/16 запросов в сходящихся вариантах) и тестами.
Аудит устранил пять уязвимостей (V1–V5), остаточные риски описаны вместе с мерами.
