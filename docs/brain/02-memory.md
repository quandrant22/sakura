выносятся. Поиск проверен на КОПИИ каталога данных (сборка промпта обновляет
счётчики `hits`).

## 2. Главная проблема: «богатый богатеет»

1. Блок ПАМЯТЬ без запроса (Telegram, проактив) берёт `_top_by_importance` —
   записи с наибольшим `hits`.
2. Каждый показ в промпте делает `hits + 1`
   (`memory/db.get_memory_context`). Топ-записи набрали ~29 000 показов.
3. Вытеснение при переполнении категории (`_maybe_evict`, 50 записей) удаляет
   запись с **наименьшим** `hits`, а это новые факты (hits=0).

Итог: в промпт годами попадают одни и те же ~20 фактов (в том числе
устаревшие), а свежие факты в полных категориях (interests, patterns,
preferences — ровно по 50) вытесняются первыми. `hits` считает показы, а не
пользу.

## 3. Ночная рефлексия → self_memory

Последние 40 записей без дневника (identity 9, insight 9, observation 13,
mood_shift 5, correction 3, pattern 1), судья-LLM (background):

| Класс | Записей | Пример такого типа записи (из self_memory, обезличено) |
|---|---|---|
| правдоподобное наблюдение о своём поведении | 8 | «держалась сухо после серии сбоев» |
| непроверяемое (чувства/восприятие, которых нет) | 20 | «чувствую, как невидимая стена становится острее» |
| неверное (противоречит возможностям/фактам) | 6 | «понравилось указывать на рассогласование системного времени» (удалена 08.10) |
| техническое (о сбоях) | 6 | «выдавала один и тот же шаблонный ответ» |

65 % записей — не опора для поведения, а самоописание, которое затем
возвращается в промпт как «что Сакура помнит о себе» и закрепляет ошибки
(пример — «час ночи» и «рассогласование времени»).

Предлагаемая фильтрация:
- в промпт — только identity/insight с явным действием («отвечаю короче на команды»), не более 5;
- не сохранять записи с маркерами восприятия («чувствую», «вижу как», «слышу»), если нет подтверждающего события;
- не сохранять выводы о времени/датах/сбоях системы (они проверяются кодом, а не самопамятью);
- дневник (diary) хранить только в secret_diary, не дублировать в self_memory.

## 4. Точность поиска (20 типовых запросов)

Семантический поиск `get_memory_context(query)` на копии БД; релевантность
каждой выданной записи — судья-LLM.

| Метрика | Значение |
|---|---|
| Запросов | 20 (машина, игры, музыка, работа, собака, сервер, хобби, …) |
| Ответ найден | **7 из 20** |
| Выдано записей | 94 (≈4,7 на запрос) |
| Релевантных | 29 (31 %) |
| Шум (не по теме) | 57 (61 %) |
| Служебный мусор | 8 (9 %) |

Причины: нет порога сходства (выдаются ближайшие k, даже если они далеко);
в памяти смешаны факты о Мастере и наблюдения о Сакуре; часть «фактов» —
устаревшие состояния («находится дома», удалена 08.10).

## 5. Политика забывания — что предложить

| Правило | Где | Эффект |
|---|---|---|
| `hits` → «использовано в ответе» (по совпадению слов ответа с фактом), а не «показано в промпте» | memory/db | разорвать петлю «богатый богатеет» |
| Вытеснение по `score = польза + свежесть`, новые записи защищены 14 дней | `_maybe_evict` | новые факты выживают |
| Порог сходства для семантического поиска (ниже — не выдавать) | `_semantic_search` | меньше шума |
| TTL для состояний («сейчас дома», «устал») — 24 ч через `expires_at` | extract_and_remember | нет устаревших состояний |
| Раздельные таблицы/категории «о Мастере» и «о Сакуре» | extract_and_remember | чистый блок ПАМЯТЬ |
| Еженедельная чистка: дубли по смыслу (embedding > 0,92), пустые/служебные | новый фоновый шаг | меньше мусора |
