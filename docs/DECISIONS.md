# Решения автономной задачи (сервер)

Правило: при неясности — самый осторожный вариант; запись здесь.

| № | решение | почему |
|---|---|---|
| S1 | Пакеты для тестов (noiseprotocol, hypothesis, pytest-cov, qrcode) ставились в `/tmp/sc-extra` через `pip --target`, **не** в боевой venv `/opt/sakura/venv` | боевое окружение не трогать; в бой — через `requirements*.txt` и шаг runbook |
| S2 | ProVerif и прочие системные пакеты **не ставились** | системные изменения на проде без владельца; модель IK написана, помечена «не запускалась» |
| S3 | `SECURE_CHANNEL` по умолчанию `off` | выкатка без изменения поведения; включение — шагом runbook (`optional`) |
| S4 | Ключи и реестр — `memory/secure/` (каталог 700, файлы 600), а не `memory/*.json` | не смешивать с существующими файлами памяти; отдельный `.gitignore` |
| S5 | Словарь спаривания — 256 своих русских слов (64 бита на 8 слов) вместо BIP39 | клиенту словарь не нужен (PSK из нормализованного текста); 64 бит достаточно при одноразовости, 10 мин и 5 попытках |
| S6 | Все отказы рукопожатия — молчание и 4408 ровно в дедлайн | неотличимость неизвестного/отозванного ключа (ТЗ) |
| S7 | `device_id` при Noise берётся из реестра, а права master — по-прежнему по `MASTER_DEVICES` | спаривание не должно само давать права master |
| S8 | Соединения с loopback/адреса сервера = secure только для приватных классов; аутентификация (токен/ключ) нужна всегда | ТЗ (клиенты через локальный xray) + защита от пользователей VPN (T5) |
| S9 | Приватные классы в proto-v2-rest без модуля политики считаются НЕ secure (отказ) | если rest выкатят раньше securechannel — приватное не откроется по ws:// |

## Несколько устройств (server/multidevice)

| № | решение | почему |
|---|---|---|
| M1 | Ветка server/integration = master + securechannel + proto-v2-rest + server-autonomy; конфликты (.gitignore, config.py, commands.py, telegram.py) — оставлены обе стороны | ветки независимы по смыслу |
| M2 | В requirements.txt `noiseprotocol` был склеен с комментарием и не ставился — вынесен на свою строку | без него securechannel на проде не поднимется |
| M3 | Активное устройство одно — `presence_sync.get_active_device()`; `device_manager.get_active_device()` делегирует, `update_device` поле active_device больше не пишет | два источника + «последний ping» → скачки при трёх ПК |
| M4 | Пороги переключения 5 с / 30 с в константах `SWITCH_NEW_IDLE_S`, `SWITCH_CUR_IDLE_S`; пауза `TRANSFER_COOLDOWN` убрана | пороги сами гасят дребезг, пауза задерживала бы голосовое переключение |
| M5 | Голос/текст = `voice_command` и `chat_send` от master-устройства | других путей ввода текста с ПК нет (tg_message — уведомление в Telegram) |
| M6 | Нет `input_idle_s` — прежняя оценка по БД, и только когда активного ещё нет; дальше его меняют голос/текст или клиент с `input_idle_s` | иначе старые клиенты скакали бы, как раньше |
| M7 | Треки: `state.device_tracks`; глобальный `_current_track` удалён; «лайк/дизлайк» берут трек устройства, приславшего команду | иначе треки ПК смешиваются |
| M8 | Трек старше 60 с не учитывается (и у активного) | агент перестаёт слать current_track, когда музыки нет, — запись иначе висела бы вечно «играет» |
| M9 | `secure_devices`: «защищённый» = как у приватных классов (Noise или локальный источник), но проверка в обработчике не зависит от `PRIVATE_REQUIRES_SECURE` | список устройств не должен открываться отключением флага |
| M10 | `fingerprint` — 16 hex отпечатка без пробелов; `revoked` — bool | первые 16 символов, ключи не отдаём |
| M11 | proto 1: mood_update только `{"is_arrival"/"is_departure": true}` без параметров настроения | «только с is_arrival/is_departure» |
| M12 | `MOOD_BROADCAST=off` гасит только отправку в `broadcast_mood`; обновление вектора настроения продолжается | настроение влияет на промпт |
| M13 | Любой `device_id` из ping заводится в devices.json под своим id; `KNOWN_DEVICES` доливаются в старый файл | на проде devices.json без mostech: раньше ping от него молча игнорировался |
| M14 | `parse_device_from_text` не менялся | исполнение команд не менять |
| M15 | Агент (`agent/`, `desktop/`) не тронут: `input_idle_s` клиенты начнут слать отдельно, до тех пор работает прежняя логика | ограничение задачи |
| M16 | `note_input` и `announce_presence_transfer` идут фоновой задачей `spawn(..., name="presence-input")`, ошибки — в лог | голосовой ход не ждёт присутствие; цена: активное устройство обновляется на доли секунды позже начала хода |

## Память задач и реальное присутствие (server/presence-memory)

| № | решение | почему |
|---|---|---|
| P1 | Задачи из обычной речи не создаются (вызов `extract_tasks_from_text` убран из `extract_and_remember`, сама функция удалена). Задача — только по явному «напомни завтра/…/добавь задачу …»: триггеры `task.add`, `tasks_add` разбирает дату/время (`tasks.parse_due`), `reminders_add` без «через N минут» но с датой отдаёт в `tasks_add` | «надо/нужно/завтра» в любой фразе засоряли память |
| P2 | Нити выключены флагом `THREADS=off` по умолчанию (`extract_threads`, `get_threads_context`, `get_thread_recall` — no-op); код не удалён | «открывать только по незакрытому вопросу Сакуры» — отдельная разработка; пока проще выключить |
| P3 | В промпт — только не выполненные и не напомненные задачи; просроченные > 24 ч (по `due_date`+`due_time`, без времени — до 23:59) уходят в `memory/tasks_archive.json` при любом чтении задач | висели в промпте вечно |
| P4 | Очистка: `modules/task_cleanup.py` (одна логика для `scripts/cleanup_tasks.py` и `/забудь_задачи`); копия `tasks.json` и таблицы `conversation_threads` (JSON) в `memory/backup/<дата>/` до удаления; нити закрываются (`closed=1`), не удаляются | откат возможен; `--dry-run` ничего не пишет |
| P5 | `/забудь_задачи`: счёт и кнопки «Да/Нет» (callback), только Мастер; `/чистыйлист` не тронут | подтверждение без перехвата обычных сообщений |
| P6 | Присутствие считается по `connected_devices` (ПК = не телефон) и вводу; нет данных о ПК (запись не пингует) — считаем, что Мастер там; клиент без `input_idle_s` — по последнему голосу/тексту, иначе по моменту появления | старые клиенты не должны «пропадать»; в тестах и сразу после подключения не блокируем озвучку |
| P7 | Порог «отошёл» — 10 мин (`AWAY_AFTER_S`); `at_work`, если ближайший к вводу ПК — `WORK_LAPTOP_DEVICE`; при простое > 10 мин на mostech — `away_from_pc` | `at_work` — про того, кто работает прямо сейчас |
| P8 | `bye` — не закрывает сокет и не требует ответа; пометка снимается следующим `register`/`ping` | клиент мог передумать (отмена выключения) |
| P9 | В промпте реальное присутствие главное; расписание — только при `pcs_off` (добавляется «по расписанию: …» и в директиву); при `away_from_pc`/`pcs_off` окно не определяет «играет»/«в коде» | окно просто осталось открытым |
| P10 | Гейт «не на ПК» стоит в двух общих точках: `stream_tts_to_device(reply_kind="proactive")` и `voice_turns.broadcast_reply(kind="proactive")`; Telegram-отправки не затронуты. Ответ на голос, сказанный на ПК, не гейтится (ввод сам делает ПК активным) | покрывает напоминания, капсулы, факты, уведомления, чайник, достижения |
| P11 | «Устройство X недоступно» убрано для ПК (`presence_sync.is_pc`), остался для остальных (телефон); серверные диск/память/нагрузка без изменений | выключение ПК — норма |
| P12 | Уточняет P6/P7: устройство, ни разу не приславшее `input_idle_s` (сейчас — все клиенты), пока онлайн даёт `at_pc`/`at_work` (простой неизвестен, в промпте без минут); `away_from_pc` — только по реальному `input_idle_s` ≥ 10 мин. Приславшее поле хоть раз судится по нему и дальше (голос/текст возвращают присутствие). Запасной «по последнему голосу» убран | без поля «отошёл» через 10 минут тишины ошибался бы на играющем Мастере |

## Питание ПК (server/power)

| № | решение | почему |
|---|---|---|
| W1 | Подтверждение выключения/перезагрузки/сна — отдельный модуль `sakura_core/power_confirm.py` (одно висящее подтверждение в `state._pending_power`), а не v3-Session: executor перехватывает `system.shutdown/restart/power.sleep` до Session | Session привязана к источнику и одному устройству; нужен ответ откуда угодно и выбор машины |
| W2 | `system.sleep` удалён из реестра, `power.sleep` получил `legacy: [system:sleep, system.sleep]` и слитые фразы; реестр 123 → 122; на провод уходит `power.sleep` | одно действие вместо двух; golden-файл переписан (system.sleep → power.sleep) |
| W3 | Для старого `agent/` провод теперь канонический (`system.shutdown`/`power.sleep` + `confirmed`), а не `system:shutdown`; `agent/` не менялся | требование задачи; **проверить на старом агенте `power.sleep`** — он знает `system.sleep` (docs/RUNBOOK) |
| W4 | Выбор ПК: все → рабочий/мостех → ноут → игровой/пк (порядок важен: «рабочий ноутбук»); без названия — активный, иначе источник, иначе единственный онлайн; иначе вопрос «Какой компьютер?» | детерминированно, без LLM |
| W5 | Вопрос идёт источнику (голос + reply `kind=confirm`), а при источнике Telegram или Мастере не у ПК — в Telegram с кнопками; «да» в Telegram принимается и без кнопок | «туда, где Мастер» |
| W6 | Посторонняя реплика вопрос не отменяет (ждёт до 60 с), в отличие от прежнего подтверждения | «да» с другого устройства и пересланные реплики не должны сбрасывать вопрос |
| W7 | Таймер 60 с (`TTL_S`) сообщает «Отменила, ничего не выключаю» туда же, где спросили; старая кнопка (другой id) игнорируется | защита от устаревших кнопок |
| W8 | `bye` и `set_offline` снимают ПК из висящего вопроса (через `presence_sync._drop_power`); нет целей — вопрос снят молча | ПК уже ушёл |
| W9 | `reply.kind="confirm"` добавлен в `REPLY_KINDS` | отличать вопрос от обычных ответов |
| W10 | Тесты, закреплявшие прежний диалог (`test_smoke` pending-system, `test_pc_control` для power.sleep, `test_registry` 123, golden), обновлены; автоочистка `_pending_power` в `conftest` | поведение изменено по заданию |
| W11 | Вопрос о питании снимается («Хорошо, не выключаю»), если Мастер сказал что угодно кроме да/нет (хук `handle_answer` стоит первым и в голосовом/оконном ходе, и в тексте Telegram; сама реплика обрабатывается как обычно), либо Сакура задала другой вопрос: `Session.expect` зовёт `power_confirm.supersede`, а для старых ожиданий (`_pending_plan/_clarify/_pending_system`, забыть-память) проверка при ответе | «да» только на последний вопрос; реверс W6 (там посторонняя реплика вопрос не трогала) |
| W12 | Наш вопрос, в свою очередь, снимает прежние ожидания (`Session.cancel`, очистка старых словарей) | порядок «последний вопрос» симметричен |
| W13 | Имена команд по proto: proto 2 — `system.shutdown`/`system.restart`/`power.sleep` + `confirmed: true`; proto 1 — `system:shutdown`/`system:restart`/`system:sleep` как раньше (без `confirmed`/`id`). Отменяет W3 | старый agent/ не менялся и знает только прежние имена |
| W14 | Нет названия, нет активного ПК, онлайн > 1 → вопрос «Какой компьютер: …?» (стадия `which`, 60 с); ПК-источник как запасной выбор убран | «без названия → активный ПК», иначе спрашиваем |


## Зрение (feat/vision)

Механика взгляда, слежения и анти-повтора — по мотивам [capri-desktop](https://github.com/lachydotmcg/capri-desktop) (PolyForm Noncommercial); код не переносился, реализация своя.

| № | решение | почему |
|---|---|---|
| V1 | Кадр экрана снимает клиент **только по запросу сервера** (`vision.capture` → `vision.frame`) или по явному действию (`window_ask`). Тихий цикл `screen_context` удалён из клиентов (ветка fix/no-silent-capture); сервер тип принимает и отбрасывает без анализа | снимок каждые 5 мин без согласия, без фильтра приватных окон и без secure-канала |
| V2 | Поддержка — `"features": ["vision.capture"]` в `register`; нет поля — прежнее значение не трогаем, не список — пусто | согласование без версии протокола; старые клиенты не ломаются |
| V3 | Кадр — приватный класс: master-only, secure-канал при `PRIVATE_REQUIRES_SECURE`, в лог — только устройство/цель/КиБ/итог; `Frame.__repr__` без байтов | как `vision_request` |
| V4 | Модель зрения — только `VISION_MODEL_CHAIN`, без инструментов; прямые `get_active_key`/`MAIN_MODEL` из пути описания экрана убраны | текст на экране не должен ничего запускать; единая цепочка |
| V5 | `screenshot.describe` → legacy-имя `vision.ask` (executor=vps). Клиент без `vision.capture` получает прежнюю команду `screenshot.describe` с вопросом в `st._pending_describe`; ответ — `describe_legacy` тем же промптом | старый `agent/` продолжает работать до перехода на `desktop/` |
| V6 | Исправлено: `_pending_describe` нигде не выставлялся — «что у меня на экране» отправляло **фото в Telegram**; при описании кадр дополнительно уходил в Telegram (`if`/`else` двумя цепочками). Теперь три случая строго взаимоисключающие, в Telegram — только `screenshot.run` | баг |
| V7 | Взгляд выключен по умолчанию (`memory/vision_settings.json`), включается голосом `vision.glance.on`; поверх — `VISION_GLANCE` | согласие Мастера |
| V8 | Интервал `GLANCE_BASE_MIN × U(0.6, 1.4)`, первый взгляд через 5–15 мин после включения; лимиты 3 кадра/ч, 6 реплик/сутки, 15 мин после своей реплики, 2 мин после хода; ночь 23–8 | «в случайный момент, но не часто» |
| V9 | Гейты повторяются **перед тем как сказать** (ход, вопрос, тишина, «занят») + сверка заголовка окна из последнего ping с заголовком кадра | модель думает секунды — за это время Мастер мог заговорить или сменить окно |
| V10 | Гейт не пройден — повтор через 5 мин, а не через полный интервал; `day_limit` — через час | не пропускать взгляд из-за мгновенного состояния |
| V11 | Ответ взгляда `ВИДЕЛА: … СКАЖУ: …`; `ПРОПУСК` допустим; неуверенность в ВИДЕЛА («кажется», «не видно») → молчание и не в память | маленькие модели угадывают игру по размытой картинке |
| V12 | ВИДЕЛА пишется в `vision/seen` (TTL 30 мин) и попадает в промпт через `get_screen_context()` даже при молчании | «что ты видела?» получает правду |
| V13 | Анти-повтор `modules/repeat_guard.py`: общие ключи (имена/названия/числа) или `is_semantically_similar` с репликами за час; модели заранее показываются последние 6 реплик | не «опять этот босс» каждые полчаса |
| V14 | Игровой event-тик (`proactive_loop`, `screenshot:` агенту во время игры) — только при включённом взгляде | это тоже снимок экрана без запроса |
| V15 | Доставка взгляда — голос на ПК, где снят кадр (`reply_kind="proactive"`, гейт P10) + `add_recent_message` для общей дедупликации проактива; в Telegram не уходит | реплика о том, что на экране, уместна только у экрана |
| V16 | Снимок `registry_golden.json` правился точечно (96 переименований `screenshot.describe → vision.ask`, +216 фраз зрения), не пересборкой | снимок отстаёт от реестра на ~2000 фраз pc-control; пересборка смешала бы чужие изменения |
